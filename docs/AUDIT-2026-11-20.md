# Full e-commerce audit: Swadeshi Mahadev Products

**Date:** 20 Nov 2026  
**Scope:** whole repo (storefront, backend, database, payments, shipping, admin, security, SEO, tests) plus read-only checks on the live site `swadeshimahadevproducts.in`.  
**Mode:** read-only. No code, config or live data changed during the audit.  
**Before the audit:** at the owner's request, commit `f84cbf2` was pushed (branch `chat-assistant`) and deployed to Hostinger (build `01a1f594`).  
**Builds on:** `AUDIT.md` (17 Nov). All P0/P1 items from that audit are fixed in code.

Status labels: **CONFIRMED** = seen in code (or live with curl), **NEEDS VALIDATION** = likely but not proven, **NOT FOUND** = searched and not present, **BLOCKED** = can't be checked from the repo.

## A. Executive summary

### Good, working today

- **Money flow:** prices come from the server, and gateway status is re-checked on the server. The PayU hash and the Cashfree webhook signature are checked.
- **Order safety:**
  - Stock is held for 30 minutes and released if payment doesn't finish.
  - The order row is locked before payment updates and refunds.
  - Coupons are reserved inside order creation.
  - Order status changes follow a fixed allowed-moves map.
  - A late or extra payment is flagged on the order.
- **Shipping:** NimbusPost booking, labels, pickup, tracking and NDR. Parcel weight and box size come from the client's packaging sheets. Per-order limits redirect to the bulk form.
- **Security basics:**
  - Admin session is re-checked (with a DB version check) on every action.
  - Rate limits on OTP, login, forms, chat and tracking.
  - Cookies are httpOnly + sameSite. CSP is set.
  - Uploads are signed and limited by format and size.
  - Admin rich text is escaped before it renders.
  - Customer invoice and credit-note routes check that the order belongs to the customer.
- **Domain:** `.com` → `.in` is a 301 that keeps the path, and `www` → apex is a 308 (both checked live).

### Risky or broken

- **Admin roles:** what the sidebar hides is not blocked on the server (AUD-001).
- **Live data:** the live DB is behind local; products the client pulled are still buyable live (AUD-002).
- **Cashfree:** live go-live isn't done, and the site could be switched to sandbox mode (AUD-003).
- **Money reporting:** the dashboard "net" is wrong when there are full refunds (AUD-005).
- **Help desk:** customers can't see the team's replies (AUD-006).
- **Testing:** no CI, no error monitoring, no tests for the new money and shipping code (AUD-010).

## G. Customer journey / state transitions

```text
Browse → Cart (server limits) → Checkout (OTP, address, pincode quote, coupon)
  → createOrder: stock held 30 min, coupon reserved
      COD    → cod_pending → confirmed → packed → shipped → delivered
      Online → pending_payment → payment attempt
                 PayU redirect | Cashfree popup (session reused for 10 min)
                 → callback / webhook / reconcile → markPaid → paid → confirmed → …
Delivered → return request (unboxing video required, 7 days) → admin review → refund
```

| Scenario | What happens | Status |
|---|---|---|
| Double-click Place Order | Same cart + method + amount within 10 min returns the same order | Handled |
| Popup closed / unpaid | Attempt stays open; retry allowed | Handled |
| 30 min with no payment | Stock released, order `payment_failed` | Handled |
| Late success after expiry | Stock re-held, or flagged "extra" if the order was cancelled | Handled |
| Two tabs both pay | Second success flagged "extra payment, refund needed" | Handled |
| Duplicate webhook | Payment already success → "duplicate", no side effects | Handled |
| Two refunds at once | Order locked; second sees the first | Handled |
| Refund timeout | Row stays `requested`, blocks a second refund, admin flagged | Handled |
| Cancel paid online order | Customer sends cancel request; team refunds | Handled |
| Cancel after courier booking | Blocked | Handled |
| Cashfree amount mismatch | Stays pending, no flag | **Gap (AUD-004)** |
